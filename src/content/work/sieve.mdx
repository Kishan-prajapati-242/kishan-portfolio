## Why it exists

I hand-screened over 200 papers for a literature review once. It took weeks, and partway through I realised I was doing a job a computer should be doing. Sieve is that computer.

It holds 182,853 research papers. You can search it by keyword, which is what you want when you know the exact name of a dataset, or by meaning, which is what you want when you can only describe the idea. It does both at once and comes back in about 10 milliseconds. It runs on a MacBook Air with 8 GB of memory and no fan, and it cost nothing to build.

The first real search I ran returned the same paper three times in the top 20. Fixing that turned into a third of the project.

## Stack

Python 3.12, FastAPI, Uvicorn, Pydantic v2, psycopg 3, raw SQL on every search path with no ORM. PostgreSQL 16 with pgvector, HNSW and halfvec, pg_trgm, tsvector plus GIN full text, JSONB, generated columns, forward-only migrations, connection pooling. Embeddings from bge-small-en-v1.5, 33M parameters, 384 dimensions, ONNX Runtime, CPU only, 512 token window. React 18, Vite, TypeScript, Tailwind, TanStack Query. Docker Compose for the whole stack with no host dependencies, Podman on macOS. pytest, ruff, mypy, GitHub Actions CI.

Hardware: M1 MacBook Air, 8 GB RAM, fanless, no GPU.

## The embedding pipeline

182,853 papers embedded, 100 percent coverage, stored as `halfvec(384)` in fp16 at 768 bytes per row. Measured throughput was 13.2 docs per second in-container, fp32, length-sorted. Projected wall clock was 248 minutes and the actual run took over 10 hours, a 2.4x miss caused by thermal throttling on fanless hardware. Peak RSS during encode was 2.05 GB. The boilerplate re-encode handled 3,847 papers title-only in 41 seconds, 94 docs per second, against a blocklist of 932 abstract hashes.

## The vector index

HNSW at m=16 and ef_construction=64. Build time was 36 seconds for 196,893 halfvec(384) rows, parallel across 2 workers. `maintenance_work_mem` needed 1 GB, and the 64 MB default would have silently taken the spill path. `/dev/shm` needed 2 GB, and Docker's 64 MB default killed the build instantly.

Recall plateaus in the 0.989 to 0.990 range by ef=640. The limit is the m and ef_construction build parameters, not search depth.

## Adjacent-rank spacing

The raw number is uninterpretable on its own: twin papers' embeddings differ by a median cosine distance of 0.0027. So instead I measured the median cosine distance between adjacent ranks inside a top-10 result set. That is 0.00213, with the rank 10 to 11 boundary at 0.00071. A stale vector therefore sits at 1.3x the adjacent-rank gap at the median and 43x at p90. It is large enough to reorder results, and at p90 it can push a paper out of the top 10 entirely. That reversed my starting assumption, which was that stale vectors were cosmetic.

## What bm25 actually does

Per-query SQL latency against bm25 match count gives Pearson r = 0.663 and Spearman 0.293. The Spearman is low because the median query matches exactly one document, so the correlation is entirely tail-driven, which is what a p95 floor looks like. The widest query matched 81,489 documents at 935.4 ms and the narrowest matched 0 at 12.8 ms. The cause is that the bm25 CTE ranks every match before applying LIMIT, so cost tracks match count rather than result count.

**The AND-semantics cliff.** `to_tsquery` requires every term to appear in the same document, so bm25 returns zero rows for long natural-language queries. Measured example: "reducing the reading difficulty of health leaflets for people with low literacy" returns nothing. Two consequences: keyword mode has a failure class on exactly the phrasing users actually type, and hybrid silently degenerates to vector-only on those queries because RRF receives only one input.

## Where each mode wins

bm25 wins on `i2b2 2010 relation extraction challenge`. The exact identifier anchors it, while vector drifts to generic relation-extraction methods.

Vector wins on `reducing the reading difficulty of health leaflets for people with low literacy`. bm25 returns zero rows on AND semantics, and vector's top 4 are all on topic.

Hybrid beats both on `making medical documents easier to understand for patients`. Its top 3 is the union of bm25's unique find and vector's pair.

On `clinical text simplification`, mutual agreement beat either ranker's individual confidence. A paper bm25 buried at rank 33 reached hybrid number 3 on the strength of vector rank 4.

## Design decisions

Python and FastAPI over Node and Express, because the embedding model is Python-native, so Node forces two services, a network hop, two deploy targets, and two dependency sets.

Year-stratified corpus sampling over citation sort, because citation count is largely a proxy for age, so sorting by it excludes the recent work the eval queries target and makes BM25 look better than it is.

Retracted papers kept and flagged rather than excluded, because a systematic reviewer needs to see a retracted paper in order to exclude it deliberately, and to check what cites it.

Null the embedding at the write site rather than track a content hash, because a hash column creates a second invariant that every text-mutating path has to maintain, and forgetting it yields a stale vector the system believes is fresh.

Reciprocal Rank Fusion over score addition, because BM25 returns an unbounded score whose scale depends on corpus and query length while cosine similarity has a different bounded distribution. RRF discards scores and keeps ranks, so it needs no per-query calibration.
